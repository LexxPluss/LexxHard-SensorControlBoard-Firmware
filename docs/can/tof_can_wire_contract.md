# ToF grid CAN wire contract (AMRSW-2322)

Contract version: **2026-08-02e**
Status: **frozen** for implementation. Everything below is normative except the numeric CAN IDs,
which are pending allocation and MUST be injected as constants/configuration.

This document is the single source of truth shared by two repositories:

- `LexxHard-SensorControlBoard-Firmware` — the **packer** (SCB firmware ToF controller)
- `LexxHard-SCBDriver` — the **decoder** (`receiver_tof` CAN path)

Both MUST be tested against the same golden vectors, generated by `gen_golden_vectors.py` into
`tof_grid_golden_vectors.json` and `tof_contract_vectors.h`. The generated artefacts carry the
SHA-256 of **this file**, and each repository pins that SHA in a test. Editing this document
changes the SHA and fails both pins until the vectors are regenerated and the pins updated
deliberately.

## Scope

Covers the 8x8 grid transport for the two VL53L7CX hanging-detection sensors. The four VL53L4CX
drop-sense sensors use a different, single-frame format on a different CAN ID and are **out of
scope here**; they are specified separately.

## Transport

CAN classic, 11-bit identifiers, on **CAN2 at 1 Mbit/s** (the SCB-to-IPC bus). CAN1 at 500 kbit/s
is the BMU bus and is not used.

Two identifiers are required:

| Constant | Meaning | Value |
| --- | --- | --- |
| `TOF_GRID_DATA_ID` | all data frames, both sensors | pending allocation |
| `TOF_GRID_HEALTH_ID` | all health frames, both sensors | pending allocation |

The 0x2xx space is used in both directions across both repositories, and apparent gaps are not
evidence of availability — `0x203` is the driver's PGV direction frame and `0x204` is the
ultrasonic frame. IDs MUST come from the company allocation table. Until then, neither repository
may hard-code a literal; both take the value from a build-time constant (firmware) or a ROS
parameter (driver), and the golden vectors carry no ID field.

Source identity is carried **in the payload**, not in the identifier. This keeps every frame of one
grid on a single identifier and costs one ID pair instead of one pair per sensor.

## Source identity

`source_id` is a **stable logical identifier**. It is not the chain position, and the decoder does
not know the chain order:

| `source_id` | Meaning | Driver topic |
| --- | --- | --- |
| 0 | `hanging_front_right` | `low_object_right` |
| 1 | `hanging_front_left` | `low_object_left` |

The firmware owns the `chain_position -> source_id` mapping and is the only place the physical
topology appears. If the boards are re-ordered on the chain, or a board is swapped, only the
firmware table changes; the wire format and the driver are untouched.

`chain_position` is still reported, in the health frame, for diagnostics only. Nothing in the
decoder may branch on it.

Note that `source_id 0` being the **right** sensor reverses the legacy SCBDriver convention, in
which the lower id was the left sensor. Now that the id is a free logical choice rather than a
consequence of chain order, the reversal is deliberate and must be carried explicitly rather than
inherited by assumption. The decoder maps id to topic through the table above, never by arithmetic.

Only `source_id` 0 and 1 exist. A frame carrying any other value is malformed.

The model ID read at enumeration validates the **part type** expected at each chain position. It
cannot distinguish the two identical VL53L7CX from each other, so it is a type check, not an
identity assignment.

## Data frame

DLC 8, always. Sixteen data frames carry one 64-zone grid.

```
byte 0 : generation           (uint8, wraps 255 -> 0)
byte 1 : source_id << 4 | chunk_index
byte 2 : z0[11:4]
byte 3 : z0[3:0] << 4 | z1[11:8]
byte 4 : z1[7:0]
byte 5 : z2[11:4]
byte 6 : z2[3:0] << 4 | z3[11:8]
byte 7 : z3[7:0]
```

The 12-bit big-endian packing is byte-for-byte the same scheme already used by
`zcan_uss.hpp` for the ultrasonic frame, so a reader familiar with one can read the other.

- `chunk_index` occupies the low nibble, range 0-15. Chunk `k` carries zones `4k` through `4k+3`.
- Zone order is **row-major**, matching the 64-element `Float32MultiArray` the driver publishes.
- Each zone is an unsigned 12-bit distance in **millimetres**. Conversion to metres stays in the
  driver (`x 0.001`, unchanged from today).
- `0xFFF` is the **invalid sentinel**. The maximum valid distance is therefore **4094 mm**.
  Firmware clamps longer valid readings to 4094; the ROS side's 3.0 m range filter discards those,
  which fails in the "no obstacle" direction and is correct for a distant target.
- `0xFFE` and below are ordinary distances. `0x000` is a valid reading, not a sentinel.

Zones the firmware judges untrustworthy — VL53L7CX `target_status` other than 5, and 6/9 depending
on the configured confidence policy — are transmitted as `0xFFF`. The driver maps `0xFFF` to
`-1.0f`, preserving the existing published contract.

`generation` increments by one, modulo 256, for each new grid a source starts transmitting. It is
**per source**; the two sources' counters are independent and unsynchronised. Every frame of one
grid carries the same value.

## Firmware transmit obligation

**A generation may only be transmitted after one complete, successful, model-verified 64-zone read
of that sensor.** This is the rule that gives the health flags their meaning.

Consequences the firmware MUST honour:

- A sensor whose model ID did not verify, or whose address assignment failed, **produces no grids
  and no health frames at all**. It does not announce itself on this pair of identifiers.
- A read that fails part-way produces no grid. Partial reads are never transmitted, not even
  flagged as partial.
- Therefore any health flag present on a frame that closes a grid describes something that has
  **already been recovered**, or something at the **chain level**, never a current failure of the
  read the grid came from.

## Health frame

DLC 8, always. One health frame per grid per source, on `TOF_GRID_HEALTH_ID`.

```
byte 0 : generation           (matches the grid it closes)
byte 1 : source_id << 4 | 0x0 (low nibble reserved, MUST be 0)
byte 2 : valid_zone_count     (0-64, count of zones not equal to 0xFFF)
byte 3 : status flags         (see below)
byte 4 : chain_position low nibble | boards_detected high nibble
byte 5 : last error code      (device/driver specific, 0 = none)
byte 6 : reserved, MUST be 0 on transmit
byte 7 : reserved, MUST be 0 on transmit
```

Status flag bits in byte 3. All of these are **recovered or chain-level** by construction of the
transmit obligation above, so none of them gates publication:

| Bit | Meaning |
| --- | --- |
| 0 | an I2C transfer error occurred and recovered since the previous health frame |
| 1 | a data-ready timeout occurred and recovered since the previous health frame |
| 2 | chain length differs from the configured expectation |
| 3 | **another** sensor on the chain failed enumeration |
| 4-7 | reserved, MUST be 0 on transmit |

There is deliberately **no flag for a model ID mismatch or address assignment failure at this
position**. Such a sensor cannot produce a grid, so the flag could never appear on a health frame,
and a flag that can never be set is worse than no flag: it invites a decoder to handle a case the
protocol forbids.

Bit 3 is how enumeration failure becomes visible. If one hanging sensor enumerates and the other
does not, the working one reports it on every health frame. **If both fail, the pair of identifiers
goes completely silent**, which no frame can express. That residual case is the decoder's
responsibility: see the watchdog requirement below.

**Exactly which fields are reserved**, and therefore ignored rather than rejected, so that a
firmware that later populates them stays compatible with an older driver:

- status flag bits **4-7** of byte 3
- bytes **6 and 7** in full

Nothing else is reserved. In particular the low nibble of byte 1 is **not** ignored: it must be
zero, and a non-zero value makes the frame structurally invalid.

The **normalised value** of a health frame is therefore byte 0, byte 1, byte 2, byte 3 masked with
`0x0F`, byte 4 and byte 5. Every comparison of two health frames is a comparison of their
normalised values. A decoder that compared all eight raw bytes would, the moment a firmware started
populating the reserved fields, read two semantically identical frames as contradicting each other
and discard a perfectly good grid — turning forward compatibility into data loss.

For the same reason a decoder MUST NOT expose the reserved flag bits to its consumers, since there
is nothing they could correctly do with them.

`valid_zone_count = 0xFF` is **reserved** for a possible future status-only frame carrying no grid.
It is not defined yet, there is no golden vector for it, and under the current contract a health
frame with `valid_zone_count > 64` is simply malformed.

Because the health frame uses a **different CAN identifier** from the data frames, the bus gives no
ordering guarantee between the two. The health frame for a grid MAY arrive before, between, or
after that grid's data frames. The decoder MUST accept all three.

## Decoder

### Interface

The assembler is pure logic: no ROS, no SocketCAN, no wall-clock.

```
consume(can_id, dlc, payload, monotonic_time)
    -> optional<CompletedGrid>, plus diagnostic events

poll(monotonic_time)
    -> per-source status, plus diagnostic events
```

Time is supplied by the caller so timeouts are testable without sleeping.

**`poll()` is not optional.** `consume()` alone cannot detect that a source has gone silent,
because with no CAN frames arriving it is never called — the one failure mode with no input to
react to is exactly the one that most needs detecting. The ROS layer drives `poll()` from a timer,
independently of traffic.

### Watchdog

The assembler tracks, per `source_id`: `last_frame_received`, `last_grid_published`, and a shared
`startup_time` set at construction. From those it reports one of four states:

| State | Condition |
| --- | --- |
| `NEVER_SEEN` | no frame carrying this `source_id` has ever been consumed |
| `HEALTHY` | a grid was published recently enough |
| `STALE_NOT_COMPLETING` | frames are still arriving, but grids are not completing |
| `STALE_NO_FRAMES` | neither frames nor grids |

Resolved in that order, with `kSourceStaleMs = 1000` and `kStartupGraceMs = 3000`:

- `NEVER_SEEN` while no frame has been seen. It is a **reportable alarm** only once
  `now - startup_time > kStartupGraceMs`; before that it is the ordinary state of a system still
  starting up.
- Otherwise the staleness reference is `last_grid_published`, or, for a source that has never
  published, `startup_time + kStartupGraceMs`. Within `kSourceStaleMs` of that reference the source
  is `HEALTHY`.
- Beyond it, the state depends on whether frames are still arriving: within `kSourceStaleMs` of
  `last_frame_received` it is `STALE_NOT_COMPLETING`, otherwise `STALE_NO_FRAMES`.

The two stale states are kept distinct because they point at different faults. `STALE_NO_FRAMES` is
a chain, power, CAN filter or enumeration problem. `STALE_NOT_COMPLETING` means the transport is
alive and something is losing or corrupting chunks, which is the failure the assembly counters
describe in detail.

A source returning to publication clears the state back to `HEALTHY`, and the transition is
reported so an operator sees recovery, not just onset.

**Staleness is a separate threshold from the 300 ms assembly timeout** and must not be derived from
it. The assembly timeout bounds how long one grid may take to arrive; staleness bounds how long the
robot may go without a usable grid from a source. The first is a protocol detail, the second is a
safety-visible property, and they will not move together.

### State

One assembly slot per `source_id`, holding: `generation`, a **16-bit chunk bitmap**, the 64 decoded
zones, the arrival timestamp of the slot's first frame, and the health frame if seen.

- **Keying is by `(source_id, generation)` equality, not by chunk ordering.** Chunks MAY arrive in
  any order. This is deliberately stronger than requiring consecutive indices: it tolerates
  reordering and duplication, and it does not depend on the CAN controller's transmit queue
  preserving order.
- A frame whose `generation` differs from the slot's starts a **new** grid. Any partially filled
  previous grid is discarded and counted. Because the comparison is equality, the 255-to-0 wrap
  needs no special case and is not a regression.
- A chunk whose bit is already set and whose payload is **identical** is a benign retransmission:
  counted, discarded, the slot continues. A health frame repeated with the same **normalised value**
  is treated the same way; a difference confined to the reserved fields is not a difference.
- A chunk whose bit is already set and whose payload **differs** retires the generation outright
  (see below). A second health frame that differs from the first does too. Two different values
  for one `(source, generation, chunk)`, or two different summaries of one grid, mean either a
  firmware fault or two data streams mixing, and in neither case is there a basis for choosing one.
- **Timeout: 300 ms**, measured from the arrival of the slot's first frame, whether that was a data
  or a health frame. On expiry the assembly is discarded, counted, and its generation retired.
  300 ms is 1.5 grid periods at 5 Hz.
- A health frame with no matching in-progress slot starts a slot holding only the health frame; it
  is not an error on its own, since it may simply have won arbitration.

### A generation is single use

Once a generation ends — **whether it published or was rejected for any reason** — the decoder
retires it. Any later frame carrying a retired generation for that source is counted and dropped;
it cannot start a new assembly.

Without this, discarding an assembly would be indistinguishable from never having seen it. A grid
rejected for a conflicting chunk, or abandoned at the 300 ms timeout, would leave no trace, and the
very frames that had just been judged untrustworthy could arrive slightly later and reassemble into
a published grid. The same applies after a successful publication: a full retransmission would
publish the same grid twice.

Only one retired generation is remembered per source, and it is overwritten by the next one. That
is sufficient because generations increment once per grid: under any traffic at all the retired
value is replaced long before the counter could wrap back onto it, and a source quiet enough for
the counter to wrap has already tripped the watchdog.

### Liveness counts malformed frames

A frame that carries a valid `source_id` but is otherwise corrupt — reserved nibble set, an
impossible `valid_zone_count` — still updates that source's last-frame time before being rejected.
It is evidence that the transport is alive.

Treating it as no frame at all would report `STALE_NO_FRAMES` and send an investigation towards the
chain, the power rail or the CAN filter, when the actual fault is corruption. A frame whose
`source_id` is not in the table is different: it cannot be attributed to any source, so it is
counted as malformed and touches no tracker.

### Publish gate

The decoder publishes a grid if and only if **all** of the following hold:

- the chunk bitmap equals `0xFFFF`, all sixteen chunks present
- the slot is not invalidated
- a **structurally valid** health frame with the same `source_id` and `generation` has been received
- the health frame's `valid_zone_count` **equals** the number of non-sentinel zones actually decoded

Structurally valid means: DLC 8, `source_id` in the table above, byte 1 low nibble zero, and
`valid_zone_count <= 64`.

A `valid_zone_count` disagreement is a **rejection**, not a warning. The packer contradicting its
own summary means one of the two is wrong and there is no way to tell which, so the zone data
cannot be trusted either. It is counted and raised as an operator-visible diagnostic. The
alternative — publishing with a warning — would leave the field with no contract value at all, in
which case it should not be on the wire.

The status flags, `chain_position`, `boards_detected` and the last error code are **diagnostic and
do not gate**. Given the firmware transmit obligation, every flag that can legally appear on a
grid-closing health frame describes an already-recovered or chain-level condition, so gating on
them would discard a grid that is by construction good.

Publishing nothing rather than a partial grid is the deliberate choice: a missing chunk left at the
sentinel decodes downstream as "no obstacle", which fails in the unsafe direction.

The watchdog is what catches total silence — both sensors failing enumeration, the chain losing
power, the CAN filter being misconfigured — because in those cases no frame is sent and every
frame-level check is vacuous.

### Diagnostic events

From `consume()`: `GRID_PUBLISHED`, `INCOMPLETE_BY_TIMEOUT`, `INCOMPLETE_BY_GENERATION_CHANGE`,
`DUPLICATE_CHUNK_IDENTICAL`, `CONFLICTING_CHUNK`, `DUPLICATE_HEALTH_IDENTICAL`,
`CONFLICTING_HEALTH`, `MALFORMED_HEADER`, `HEALTH_COUNT_MISMATCH`, `ORPHAN_HEALTH_TIMEOUT`,
`FRAME_FOR_RETIRED_GENERATION`.

From `poll()`: `SOURCE_NEVER_SEEN` (once past the startup grace), `SOURCE_STALE`,
`SOURCE_RECOVERED`. These are **edge triggered**: a ROS layer polling at 10 Hz must not receive one
event per tick for a condition that has not changed. An alarm is raised once and cleared once, and
`SOURCE_RECOVERED` fires wherever recovery happens, including on the first grid ever received from
a source that had already been alarmed as `NEVER_SEEN`. An alarm that can be raised but never
lowered is worse than no alarm.

Draining the event queue **removes** the events. Callers process each one exactly once; leaving
them in place would replay the entire history on every spin.

Together these feed the operator-visible diagnostics that the ROS side needs to replace its
silent-degradation paths.

## Bus load

Seventeen frames per grid per source. At 5 Hz with both hanging sensors, on CAN2 at 1 Mbit/s, this
is about **2.24%** occupancy including stuff bits and inter-frame space. The four-zone layout costs
0.39 percentage points more than a five-zone layout would, and buys sixteen header bits instead of
four — enough for the generation counter, the chunk index and the source id simultaneously, with no
spare packing slot to define, since 16 x 4 is exactly 64.

## Golden vectors

`gen_golden_vectors.py` is the normative reference packer. It emits both
`tof_grid_golden_vectors.json` and `tof_contract_vectors.h`, a dependency-free C++ header so that
neither repository needs a JSON parser in its test build. Both carry the SHA-256 of this file.

Both repositories MUST decode the vectors to the stated grids and, on the firmware side, MUST
reproduce the byte sequences exactly.

Cases covered: an ordinary ramp, an all-invalid grid, boundary values (0, 1, 4093, 4094, 0xFFF),
the 255-to-0 generation wrap, both sensors interleaved, and the rejection paths — loss, timeout
boundaries, conflicting duplicates in both the chunk and health frames, count mismatch, malformed
headers, a cross-grid splice attempt, a retired generation attempting to revive, and the watchdog
states including recovery from a `NEVER_SEEN` alarm.

Each scenario declares the **complete multiset** of events it must produce, not merely one event it
must contain. An event that is not listed must not occur even once, so an implementation cannot
pass by emitting the right event alongside several wrong ones. Every scenario also ends with an
explicit `poll`, so the expected multiset is fully determined by the vector rather than by whatever
the test harness happens to do at the end.
