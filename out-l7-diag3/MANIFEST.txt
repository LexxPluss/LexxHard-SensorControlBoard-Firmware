WHAT IT IS, AND WHAT IT IS NOT

Mode 1 (diag1-v5) ran thirty minutes armed on dasher2 with the ISR backport and did not wedge:
187,000 port transactions, 70 million I2C interrupts, orphan_rxne 0. It proved the firmware can
READ the real L7. It then dropped every grid frame at the last step, which is why nothing above
the SCB -- driver, assembler, detector -- has ever seen a real L7 distance.

Mode 3 removes that one drop and nothing else. It is NOT a step towards release. It is still DEV,
still NO-FAT, still safety-lidar bypassed, still unconfirmed, and the robot is still not driveable.

WHAT STILL HAS TO HAPPEN BEFORE THIS IS FLASHED

  A clean E3 starting point, established by a full battery power cycle. After any run that opened
  the L7, E3 cannot complete commissioning.

  WHAT IS PROVEN, AND WHAT IS NOT. Proven: SOME L7 internal state survives an SCB-only reset, and
  only cutting the sensor power rail clears it. An SCB or MCUboot reset restarts the STM32 but does
  not reliably drop power to the ToF chain, while E3 comes up and re-enumerates the chain as if
  from cold -- hence scb_attempts_exhausted, roles 255 and 0x216 at zero. NOT proven: which state
  it is. Downloaded ULD, an active ranging session, a latched address, an unfinished transaction
  are all consistent with what has been observed, and nothing so far distinguishes them. Earlier
  copies of this note said "half-finished transaction state", which claimed one of those without
  evidence.

  Checks for the clean point: E3 3.6.0-144-gdd12e1b7 confirmed, commissioning finished, four roles,
  0x216 about 200 frames/s, blob still committed/valid.
